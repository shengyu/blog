很多团队第一次做 AI agent 时，直觉上会把它当成“数字同事”：给它一个目标，补一点上下文，然后期待它自己拆解任务、调用工具、修正错误，最后稳定交付结果。

这个想法很自然，但通常也是问题的起点。

在 demo 阶段，agent 看起来像一个会思考、会执行、还能自我修复的智能体；一旦进入真实环境，它暴露出来的却是系统问题：上下文不稳定、工具权限过大、状态不可追踪、失败不可重现、输出质量依赖偶然路径。很多人把这些问题归咎于模型还不够聪明，实际上更常见的原因是系统设计太松散。

我的判断是：**大多数 AI agent 项目，真正需要的不是更强的人设，而是更硬的工程约束。**

## 为什么“数字同事”这个比喻会误导团队

把 agent 当成同事，会让团队默认接受一些本不该接受的模糊性。

- 目标可以先说个大概，细节让它自己补
- 过程可以不透明，只要最后结果“看起来差不多”
- 失败可以归因为“发挥不稳定”
- 权限可以先给大一点，不够再慢慢收

这些做法在人和人的协作里可能成立，因为人类天然具备常识、责任感、环境感知和长期记忆补全能力。但 agent 没有这些默认能力。它只有当前输入、有限状态、工具接口，以及一套概率性的决策过程。

换句话说，agent 并不是一个抽象的“员工”，而是一条由若干组件拼起来的执行链：

1. 一个负责推理和生成的模型
2. 一组可调用的工具
3. 一份被裁剪过的上下文
4. 一套状态读写机制
5. 一层决定何时继续、何时停止、何时回滚的控制逻辑

只要其中任意一环定义得不清楚，整体行为就会迅速退化。

## 好的 agent，更像一条生产线

如果把 agent 看成系统，设计思路就会完全不同。

你不会先问“这个 agent 像不像一个资深员工”，而会先问：

- 输入边界是什么
- 中间状态存在哪里
- 哪些动作是允许的
- 每一步怎样验证
- 失败之后如何降级
- 日志是否足够让问题复现

这更接近生产线思维，而不是岗位思维。

一条成熟的 agent 流程，通常不是“一个大模型负责一切”，而是把不确定性压缩到少数必要节点，把确定性尽量前置。例如：

- 用规则把任务先分流，而不是一开始就让模型自由规划
- 用结构化参数调用工具，而不是让模型拼接任意命令
- 用显式检查器做结果验证，而不是让模型自评“应该没问题”
- 用状态机控制流程跳转，而不是靠 prompt 暗示“如果失败就重试”

这类设计不一定最炫，但更接近可上线、可维护、可扩展的工程现实。

## 先定义状态，再讨论智能

很多 agent 设计文档一上来就在讨论 memory、reflection、planning，听起来都很高级，但如果系统连状态模型都没定义清楚，这些能力只会让复杂度迅速膨胀。

一个实用的办法是先把 agent 的状态拆成三层：

- `working state`：当前任务临时变量，比如用户目标、已选工具、最近一次执行结果
- `session state`：一次任务生命周期内共享的信息，比如任务计划、失败次数、人工介入标记
- `persistent state`：跨任务保留的长期数据，比如用户偏好、历史工单、已验证知识

只有这三层分清楚了，团队才知道哪些信息应该进 prompt，哪些应该进数据库，哪些只该存在于一次执行上下文里。

如果所有东西都往 prompt 里塞，agent 表面上像是“记住了很多事”，实际上只是让成本、噪声和不稳定性一起上升。

## 工具越多，不代表 agent 越强

另一个常见误区是给 agent 接很多工具，仿佛能力面越广，系统就越先进。

现实往往相反。工具一多，决策空间会扩大，错误组合也会变多。真正重要的不是工具数量，而是工具接口是否足够窄、返回值是否足够稳定、失败语义是否足够明确。

一个设计良好的工具接口，至少应该满足三件事：

- 输入参数结构化，可验证，可拒绝非法调用
- 输出结果稳定，方便后续步骤消费
- 权限边界清楚，不把危险操作混在普通操作里

例如，比起给 agent 一个“执行任意 SQL”的工具，更安全的做法通常是提供几个收敛后的业务动作：查询订单、更新状态、创建草稿、提交审核。这样做会牺牲一些通用性，但能大幅降低系统行为的不可控程度。

## 验证层不是附属品，而是 agent 的一半

如果一个 agent 能写、能查、能调工具，但没有独立验证层，那它更像一个高自由度脚本，而不是一个可靠系统。

验证层至少要回答两个问题：

1. 这一步是否真的完成了预期目标？
2. 如果没有完成，系统应该重试、回滚、升级还是中断？

这意味着“让模型再检查自己一遍”通常不够。更稳的办法是引入与生成阶段不同的检查机制，例如：

- 用 schema 校验结构化输出
- 用规则校验关键字段
- 用权限系统阻止越权动作
- 用测试样例或断言校验代码结果
- 用人工确认守住高风险节点

一个成熟的 agent，往往不是因为它每次都想对了，而是因为它在想错时也不容易把事情做坏。

## 设计 agent 时，先问失败路径

很多团队讨论 agent 时，主要在画 happy path：接收任务，理解意图，规划步骤，调用工具，完成目标。

但真正决定可用性的，通常是失败路径：

- 工具超时怎么办
- 返回结果为空怎么办
- 外部系统状态变化怎么办
- 多次重试后仍失败怎么办
- 一部分动作成功、一部分失败怎么办
- 用户在执行中修改目标怎么办

如果这些问题没有在设计阶段被回答，agent 一旦进入生产环境，就会以最昂贵的方式逼团队补课。

所以我更建议把 agent 设计文档写成下面这种结构：

```text
goal -> state -> tool contract -> verification -> fallback -> escalation
```

先写清楚系统如何失败，再讨论系统如何表现得聪明。

## 真正有价值的 agent，往往都很克制

当一个 agent 最终跑得稳定，你会发现它通常没有那么“像人”。

它不会无限发挥，也不会处处自主。它更像一个被精心包起来的执行系统：

- 在少数节点使用模型做高杠杆判断
- 在大部分节点依赖确定性流程
- 在关键动作前后加验证和审计
- 在不确定性过高时主动停下来

这听上去不浪漫，但很有效。

AI agent 的未来当然会继续向更强自治前进，但在当前阶段，真正拉开差距的并不是谁更敢放权，而是谁更擅长把自治能力放进清晰的系统边界里。

**不要先问 agent 能不能像人一样工作。先问这个系统出了错以后，能不能被看见、被限制、被修复。**

这才是 AI agent 从“能演示”走向“能交付”的分界线。
