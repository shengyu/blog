很多团队做 AI agent，第一反应是“把上下文喂满”。

需求文档塞进去，聊天记录塞进去，知识库检索结果塞进去，工具返回值也全部塞进去。只要上下文窗口还没爆，就继续加。这样做短期内很有安全感，因为它看起来像是“信息更全了”。

但在真实系统里，**上下文变多，通常不等于 agent 变强；很多时候，只意味着决策空间变脏了。**

AI agent 的问题，常常不是缺信息，而是缺筛选、缺层次、缺预算意识。上下文不是一个无限仓库，它更像一种昂贵的工作内存。你给 agent 的每一段内容，都会和当前任务争夺注意力。

## 上下文本质上是一种预算

把上下文理解成预算，比把它理解成记忆，更接近工程现实。

预算意味着三件事：

- 每放进去一条信息，就要付出注意力成本
- 不同信息的价值密度并不一样
- 超过某个阈值之后，新增信息会开始稀释关键信号

这和人类开会其实很像。一个会议如果材料太少，大家无法判断；但如果会前发了二十个附件、三十页群聊截图、五份历史方案，结果往往不是讨论更充分，而是谁都抓不住重点。

agent 也是一样。模型当然可以“看到”更多文本，但“看到”和“有效使用”不是一回事。尤其当任务本身需要规划、比较、调用工具和生成结构化结果时，噪声上下文会直接降低执行质量。

## 真正有用的上下文，通常只有四类

我更倾向于把 agent 的上下文拆成四类，只让必要信息进入当前回合。

### 1. 任务上下文

这是 agent 当前到底要解决什么问题。包括目标、约束、交付格式、截止条件。

这部分必须短，而且必须明确。与其给 agent 一大段模糊背景，不如给它一段可以执行的任务定义：

- 目标是什么
- 成功标准是什么
- 哪些事情不能做
- 输出要长什么样

如果任务上下文本身含糊，后面加再多信息都只是在放大偏差。

### 2. 状态上下文

这是任务进行到哪一步了。比如：

- 已经调用过哪些工具
- 哪些结果已经确认
- 当前卡在哪个节点
- 是否需要人工确认

很多 agent 失败，并不是因为“不会思考”，而是因为它在一个长流程里不断遗失状态。它会重复做同一步，或者忘记上一轮已经排除过的分支。

状态信息应该是结构化的，而不是埋在一长串自然语言对话里。

### 3. 参考上下文

这是 agent 为了完成任务而需要临时查阅的资料，比如检索结果、文档片段、历史案例。

参考上下文最容易失控。因为团队会下意识认为“多给一点总没错”。但真正重要的不是数量，而是命中率和压缩质量。

比起一次塞十段检索结果，更有效的做法通常是：

1. 先粗筛，保留最相关的两到三段
2. 做一层摘要，把重复内容合并
3. 明确标注来源和置信度

让模型自己在一堆相似段落里找重点，本身就是在浪费预算。

### 4. 操作上下文

这是工具使用所需的即时信息，比如 API 参数、表单字段、数据库记录主键、文件路径。

这一类上下文应该尽量贴近动作本身，按需加载，而不是一直挂在主 prompt 里。否则会出现一种典型问题：agent 还没决定要不要执行动作，脑子里已经塞满了动作细节。

## 上下文管理的核心，不是“记住”，而是“取舍”

很多系统在谈 memory 时，重点放在“如何长期记住用户信息”。这当然重要，但对 agent 来说，更难的问题往往不是记住，而是知道此刻该拿什么出来。

一个实用的 agent，不应该把所有历史都摊在当前窗口里，而应该做两层工作：

- 在窗口外保留更丰富的状态和历史
- 在窗口内只放当前决策真正需要的最小集合

换句话说，长期记忆应该存在系统里，而不是一直占着模型的前排座位。

一个比较健康的上下文装配过程，通常长这样：

```yaml
task:
  goal: "分析用户反馈，输出三个可执行产品建议"
  constraints:
    - "不要杜撰用户原话"
    - "建议必须可以在两周内落地"

state:
  completed_steps:
    - "已完成聚类"
    - "已过滤垃圾反馈"
  pending_step: "生成建议"

references:
  - "近 7 天高频反馈摘要"
  - "上次版本变更记录"

action:
  output_schema: "title, problem, proposal, impact"
```

这个结构并不花哨，但它有一个好处：每类信息都有自己的位置。系统知道哪些是目标，哪些是过程，哪些是材料，哪些是输出约束。模型不需要在一团混杂文本里猜结构。

## 为什么“全量聊天记录”经常是个坏主意

很多对话式 agent 会把整段聊天历史不断回灌进去，理由是为了“保持连续性”。这件事在短流程里还能勉强成立，但在中长流程里，问题会越来越明显。

第一，历史对话里充满了阶段性假设。早期说过的话，后来可能已经失效；如果不做整理，模型会把过时信息和当前事实一起考虑。

第二，聊天记录的信号密度很低。它适合给人读，不适合直接作为机器决策材料。礼貌寒暄、路径试探、反复确认，这些对协作有意义，但对执行并不总有帮助。

第三，长聊天记录会掩盖真正关键的最新指令。最终 agent 看起来像是“没理解用户”，其实它只是被过多旧信息拖住了。

更稳的办法通常不是保留全部对话，而是在每个关键阶段生成一份新的结构化状态摘要，用它替代冗长历史。

## 设计 agent 时，可以先问这五个问题

如果你怀疑一个 agent 的上下文已经失控，可以直接检查下面五件事：

1. 当前窗口里的每一段信息，是否都服务于当前决策？
2. 有没有过时但仍被反复注入的内容？
3. 有没有本该结构化的状态，被埋在自然语言里？
4. 参考资料是否经过筛选和压缩？
5. 工具执行所需的细节，是否只在真正调用前才加载？

这五个问题里，只要有两个答不上来，agent 的行为大概率已经开始被上下文噪声拖累。

## 好的 agent，会主动把上下文变薄

很多人以为优秀的 agent 设计，是不断扩展能力边界：更多记忆、更多工具、更多检索、更多历史。

但从交付角度看，更成熟的系统往往反过来做事。它会主动限制当前回合的信息量，让模型只处理最有用、最可验证、最接近动作的部分。

这也是为什么好的 agent 体验，常常不是“它知道一切”，而是“它每次都能抓住最相关的那一点”。

上下文管理不是一个附属优化项，它本身就是 AI agent 产品能力的一部分。你给模型看的内容，决定了它能想什么；你替模型拿掉的内容，决定了它还能不能把事情想清楚。

**所以别再问：这个 agent 还能再塞多少上下文？更该问的是：为了完成当前任务，什么内容根本不该出现在这里。**
